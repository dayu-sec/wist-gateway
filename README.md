# wist-gateway

Control-plane gateway for the **wist** agent fleet.

[![Build & Test](https://github.com/dayu-sec/wist-gateway/actions/workflows/build-and-test.yml/badge.svg)](https://github.com/dayu-sec/wist-gateway/actions/workflows/build-and-test.yml)
[![codecov](https://codecov.io/gh/dayu-sec/wist-gateway/branch/main/graph/badge.svg)](https://codecov.io/gh/dayu-sec/wist-gateway)
[![dependency status](https://deps.rs/repo/github/dayu-sec/wist-gateway/status.svg)](https://deps.rs/repo/github/dayu-sec/wist-gateway)
[![License: Apache-2.0](https://img.shields.io/badge/license-Apache--2.0-blue.svg)](LICENSE)

`wist-gateway` is the center-side HTTPS service that [`wist-agentd`](../wist-agentd) agents
enroll with and report to. It exposes an admin/agent API over TLS and is the single choke point
through which the control plane hands out install scripts and packages, accepts enrollment,
collects status and host metrics, issues control commands, and aggregates execution results.

## Docs

- [docs/design/gateway-access-security.md](docs/design/gateway-access-security.md) — control-plane
  access security: trust model, per-customer CA (KMS/HSM), DNS/naming, and disaster recovery.

## Features

- **Agent install** — signed install script and package distribution, one-time enrollment tokens.
- **Enrollment** — registers agents and rotates credentials with a bootstrap-token TTL.
- **Status & metrics** — accepts agent status reports and host/process metrics, with
  per-client rate limiting.
- **Control commands** — queues `ActionPlan`s for agents to poll and receives `ActionResult`s back.
- **Admin API** — fleet overview, per-agent runtime status, pipeline topology.
- **TLS-first** — serves HTTPS with rustls and injects the real peer address for rate limiting.

## Building

```bash
cargo build --release
```

This produces the `wist-gateway` binary in `target/release/`.

The floor-machine compatibility e2e (`linux_install_command_runs_on_ubuntu_2004`) needs docker and
is skipped by default; enable it with:

```bash
WIST_GATEWAY_DOCKER_E2E=1 cargo test --lib linux_install_command_runs_on_ubuntu_2004
```

## Quick start

Generate a default config (with a freshly random admin token and install-script signing key),
then run the gateway:

```bash
cargo run -- init-config
cargo run -- --config-dir .
```

Before starting you need a TLS certificate/key pair at `state/admin-tls.crt.pem` and
`state/admin-tls.key.pem` (see the notes printed by `init-config`).

## Configuration

`wist-gateway` is configured by a `wist-gateway.toml` file (generated by `init-config`). Main
sections:

- `[server]` — listen address, public base URL, TLS cert/key, admin token, VictoriaMetrics URL,
  and `self_face_allow` (extra IPs/CIDRs trusted as "the local host" for the loopback-only faces
  `self-state` / `link-request` / `linkd-status` / `agent-package`; usually left empty — inside a
  container the gateway auto-trusts its default gateway, i.e. the host; `/0` is rejected).
- `[agent]` — package file, bootstrap/credential TTLs, store file, trust bundle, signing key.
- `[store]` — persistence DSN (`database_url`).

## Storage

Agent registry and enrollment tokens are persisted in **SQLite** (embedded, no extra service):

- Default database file: `state/wist-gateway.db`, next to the configured `agent.store_file`.
  Set `[store] database_url = "sqlite:/var/lib/wist-gateway/gateway.db"` to place it elsewhere,
  or override with the `WIST_GATEWAY_DATABASE_URL` environment variable (an explicitly empty
  value falls back to the default file). This build implements SQLite only; other schemes are
  rejected at startup.
- Schema lives in `migrations/sqlite/` and is applied on startup via `sqlx::migrate!`, so new
  tables/columns are created on an existing database too.
- The file is the whole durable state: back it up and it can be restored. Deleting it forces all
  agents to enroll again.
- Upgrading from the older single-file JSON store (`state/wist-gateway-store.json`): it is
  imported automatically on first start when the database is still empty, then renamed to
  `*.imported`. The import is skipped if the database already has data.

Agents, their instances and their credentials are separate tables: a restarted agentd adds an
instance row instead of overwriting the previous one, and credential rotation/revocation keeps
history rather than replacing the row in place.

### Install package address

The address the gateway hands out for the wist-agentd package is a managed setting rather than a
build-time constant:

- `GET /api/v1/admin/agent/install-package` — current effective address (falls back to the
gateway's own `/api/v1/agent/packages/current` route when never set; `updated_by` is empty and
`updated_at` is null in that case).
- `POST /api/v1/admin/agent/install-package` — set it. Body: `package_url` plus optional
`package_sha256` and `requested_by`. The URL must be `https://…` or an absolute path (plain `http`
is rejected — the package is what an agent boots from); the digest, when given, is normalized to
`sha256:<64 hex>`.

New install codes and freshly rendered `install.sh` use the setting; already-issued install codes
keep the address they were generated with. Both are admin-bearer authenticated and stored in the
`agent_install_package` table.

### Package sources (one-click fill)

The admin console's install-package entry can fill the three agentd artifacts from a GitHub
release or a Tencent COS prefix (the knowledge entry uses the same two endpoints and takes the
single `.tar.gz` asset):

- `POST /api/v1/admin/github-release/resolve` — `{ "release_url": "https://github.com/…" }`.
- `POST /api/v1/admin/cos/resolve` — `{ "cos_path": "<bucket>/wist-agentd/<tag>" }`; also accepts
  `cos://bucket/prefix` and a region-qualified `https://<bucket>.cos.<region>.myqcloud.com/…` URL.

Both return the same shape: `{version, assets:[{name, artifact_url, sha256, platform}]}`. The COS
resolver needs no credentials: the bucket is public-read and the sha256 is carried in the
`x-cos-meta-artifact-sha256` object metadata (COS only stores an MD5 ETag). Because the download host
contains the region, the resolver probes the usual regions in order unless the region is present in
the path or set via `WIST_GATEWAY_COS_REGION`; a whole lookup is capped at 60 seconds.

> WAL mode allows concurrent readers but only a single writer, and the database is not shared
> across hosts. Run a single `wist-gateway` replica; a shared database (Postgres) would be needed
> to scale out behind a load balancer.

## Supported target hosts (agent install)

The Linux install command the gateway hands out downloads `install.sh`, checks it against the
sha256 **embedded in the command itself**, and only then runs it. It needs **no OpenSSL**: the
previous `openssl pkeyutl -verify -rawin` path required OpenSSL ≥ 3.0, which was stricter than
every other link in the install chain (the script and agentd only ever needed systemd + curl).

Baseline a target host must provide:

- a POSIX `sh` (dash/ash are fine), `curl`, `tar` with gzip, `awk`, and `sha256sum`
  (`shasum` is accepted as a fallback — same order as `install.sh`);
- root — the script re-executes itself under `sudo` when not already root;
- Linux: **systemd as PID 1** (the only Linux service backend `wist-agentd` implements);
  macOS: launchd.

Equivalent distributions: Ubuntu 20.04+, Debian 11+, RHEL/CentOS 8+, macOS 11+ (ARM).
Out of scope: systems without systemd (EL6, Ubuntu 14.04 and older), and trimmed images that ship
neither `curl` nor `awk` — install those first, the floor does not assume them.

`WIST_AGENTD_SERVICE=0` runs the agent in the foreground and drops the systemd requirement, at the
cost of no supervised restart — for containers and other self-managed setups.

macOS keeps its own command: `curl --pinnedpubkey` authenticates the TLS channel by pinning the
gateway's serving certificate, because macOS ships LibreSSL (no Ed25519 raw verification either).

The digest is fixed **when the install code is issued** (the rendered script embeds the package
address and the package digest). Re-uploading a package or changing the advertise URL afterwards
makes an already issued command fail closed with a digest mismatch — re-copy the command instead
of reusing the old one.
